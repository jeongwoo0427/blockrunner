# 07. 되돌리기 · 다시하기 · 클리어 처리

## 목표

무제한 되돌리기, 다시하기, 이동 횟수 집계, 클리어 판정과 결과 표시를 완성한다.

## 선행 조건

- [04-game-screen.md](completed/04-game-screen.md)
- 규칙: [../game-design.md](../game-design.md) §5

## 작업

### 1. undo 스택

`BoardState`가 불변이므로 스택은 단순하다.

```dart
final List<BoardState> history;   // 이동 전 상태들
```

- `MoveRequested`가 **실제로 이동을 일으켰을 때만** 현재 보드를 push한다. 무효 입력은 쌓지 않는다.
- `UndoRequested` → pop해서 복원, `moveCount--`
- `history.isEmpty`면 undo 버튼 비활성
- 제한 없음. 8×8 보드 상태 수백 개는 메모리에 부담이 없다.

`state.copyWith`로 리스트를 갈아끼울 때 **새 리스트를 만든다.** 기존 리스트를 `add`로 변형하면 불변 규약이 깨지고 undo가 조용히 망가진다.

### 2. reset

`map.initialBoard`(state.map)로 되돌리고 `moveCount = 0`, `history` 비움, `isCleared`·`isPlayerLost` 해제.
클리어한 뒤에도 다시하기가 가능해야 한다 (더 적은 수로 재도전).

### 3. 이동 횟수

- 유효 이동에서만 증가
- undo에서 감소 (음수가 되지 않도록)
- reset에서 0

### 4. 플레이어 소실 상태

`!board.hasPlayer` → `isPlayerLost = true`.

- 방향 입력을 받지 않는다
- 되돌리기 / 다시하기 버튼을 강조해 보여준다
- **게임 오버 화면을 띄우지 않는다** — 실패 조건이 없는 게임이다 (game-design §3.5)

### 5. 클리어 처리

이동 후 `board.isCleared`이면:

1. `isCleared = true`
2. 별점 계산 (game-design §5 표)
3. `SaveClearResultUsecase` 호출 — 진행도 저장 + `yieldData()`로 스트림 방출 ([09-progress.md](09-progress.md))
4. 결과 오버레이: 별점, 이동 횟수, 최소 이동 횟수, `[다시하기] [레벨 선택] [다음 레벨]`

**최고 기록만 갱신한다.** 두 번째 플레이가 더 나쁘면 기존 기록을 유지한다.

별점 경계값(1.5배의 반올림/버림)을 여기서 확정하고 game-design §5 표를 갱신한다.
> **정정:** 1.5배 기준 자체가 폐기됐다. 아래 "실제 결과" 참고 — 초과 비율(20% · 40%)과 고정 여유 중 큰 쪽으로 바뀌었다.

### 6. 버튼 UI

`widget/game_hud.dart`에 `[↶ 되돌리기] [↺ 다시하기]` + 이동 횟수 표시.
키보드 단축키 `R`(다시하기)은 [05-input.md](completed/05-input.md)에서 연결됐다. **`Z`(되돌리기)는 이 작업에서 붙인다** — `game_play_screen.dart` 의 `_directionForKey` 옆 키 처리에 추가하면 된다.

## 실제 결과

### 되돌리기가 무제한에서 **레벨당 3회**로 바뀌었다

작업 문서 §1 은 "제한 없음" 이었지만 **사용자가 제한을 요청**해서 규칙이 바뀌었다. 기획서 §5.1 에 근거를 적었다 — 무제한이면 아무 방향이나 눌러보고 무르는 것이 최적 전략이 되어 퍼즐이 시행착오 게임이 되고, 구멍이 아무 위협도 아니게 된다.

파급된 결정 둘 (사용자 확인):

- **다시하기가 횟수를 되살린다.** 판을 처음으로 돌렸으면 자원도 처음으로. 무엇보다 막혀도 빠져나갈 길이 항상 있어야 "실패 조건 없음"(§5)이 유지된다
- **구멍에 빠졌는데 횟수를 다 썼으면 다시하기만 남는다.** 기획서 §3.5 가 "되돌리기로 복구" 를 전제하고 있어 함께 고쳤다. 이 대가가 구멍을 위협으로 만든다

### 별점은 `Level` 엔티티에 뒀다

`Level.starsFor(moveCount)`. `docs/architecture.md` §7 의 "도메인 로직은 엔티티 안에" 를 따랐고, `minMoves` 가 이미 `Level` 에 있어 자연스럽다. `game → level` 한 방향이라 새 간선도 생기지 않는다.

**별점 기준은 작업 도중 한 번 갈아엎었다.** 처음에는 문서대로 "★★★ = 최소 수와 동일, ★★☆ = 1.5배 버림" 으로 넣었는데, 그러면 `minMoves` 가 1인 레벨에서 **2수만 써도 ★☆☆** 로 떨어진다. 짧은 레벨일수록 가혹해지는 뒤집힌 난이도다.

사용자 요청으로 **초과 비율 기준**(20% 이내 ★★★ / 40% 이내 ★★☆)으로 바꿨다. 다만 현재 레벨의 `minMoves` 가 전부 1~3 이라 비율만으로는 여유가 0수가 되므로, **비율과 고정 여유(1수 · 2수) 중 큰 쪽**을 쓴다. 짧은 레벨은 고정 여유가, 긴 레벨은 비율이 지배한다. 기획서 §5.2 에 표로 못 박았다.

이 변경으로 **★★★ 가 최적해를 요구하지 않게 됐다.** 최적해만 인정하면 별점이 "풀었는가" 가 아니라 "정답을 외웠는가" 를 재게 되고, 최소 수를 모르는 상태에서는 사실상 도달 불가능한 목표가 된다.

### 되돌리기는 즉시 반영이다

`06` 에서 `isAnimating` 이 "이번 변화를 보여줄지" 를 겸하게 해둔 덕분에, `_undo` 가 그 플래그를 세우지 않는 것만으로 되감기 연출 없이 즉시 반영된다. 별도 코드가 없다.

### 되돌린 판에서 판정을 다시 낸다

`isCleared` / `isPlayerLost` 를 `false` 로 되돌리는 것이 아니라 **복원된 판에서 다시 계산한다.** 그냥 `false` 로 두면 목표 칸 위에서 무른 경우처럼 되돌린 판이 이미 클리어인 상황을 놓친다.

### 남은 사항

- **진행도 저장은 `09-progress`.** 클리어 여부 · 최고 별점 · 최소 이동 기록, 그리고 `SaveClearResultUsecase` 의 스트림 방출이 전부 거기 남아 있다
- 3회가 적절한지는 플레이해봐야 안다. `AppConstants.undoLimit` 하나만 고치면 된다
- 레벨마다 다른 횟수를 주고 싶어지면 `Level` 로 옮기면 된다 (`tutorial` 이 그렇게 들어갔다). 지금은 전역 상수로 충분하다
