# 05. 크로스플랫폼 입력

> **상태: 완료** (2026-08-05)

## 목표

모바일·웹·데스크탑에서 각각 자연스러운 방식으로 4방향 입력을 받는다. 게임 로직은 건드리지 않는다 — 전부 `MoveRequested(Direction)` 하나로 수렴시킨다.

## 선행 조건

- [04-game-screen.md](04-game-screen.md)
- 요구사항: [../../game-design.md](../../game-design.md) §6

## 작업

### 1. 스와이프 (모바일 · 터치)

`GestureDetector`의 `onPanEnd` 또는 `onPanUpdate`로 판정한다.

- 최소 이동 거리 임계값을 둔다 (예: 24 logical px). 그보다 짧으면 탭으로 보고 무시.
- 가로 성분과 세로 성분 중 **절대값이 큰 쪽**으로 방향을 결정한다.
- 대각선 스와이프를 4방향으로 강제 매핑하는 셈이므로, 두 성분이 비슷할 때의 동작을 테스트한다.

### 2. 키보드 (웹 · 데스크탑)

`Focus` + `KeyboardListener`(또는 `Shortcuts`/`Actions`).

| 키 | 방향 |
|---|---|
| `ArrowUp` / `W` | 위 |
| `ArrowDown` / `S` | 아래 |
| `ArrowLeft` / `A` | 왼쪽 |
| `ArrowRight` / `D` | 오른쪽 |
| `Z` / `Ctrl+Z` | 되돌리기 |
| `R` | 다시하기 |

**화면 진입 시 자동으로 포커스를 잡아야 한다.** 안 그러면 웹에서 키가 안 먹고, 사용자는 이유를 모른다. 다이얼로그가 닫힌 뒤 포커스를 되찾는 것도 확인한다.

`KeyDownEvent`만 처리한다. `KeyRepeatEvent`를 처리하면 키를 누르고 있을 때 연타된다 — 애니메이션 중 입력 무시 규칙과 겹쳐 동작이 어색해지므로 명시적으로 거른다.

### 3. 화면 방향 버튼

세 플랫폼 공통 보조 수단. 마우스만 쓰는 사용자와 접근성 때문에 항상 제공한다.
십자(D-pad) 배치, 보드 아래 또는 옆(가로 레이아웃일 때).

### 4. 입력 게이트

모든 입력 경로가 한 곳을 지나게 한다.

```dart
void _requestMove(Direction d) {
  if (state.isAnimating || state.isCleared || state.isPlayerLost) return;
  onEvent(MoveRequested(d));
}
```

**입력을 큐잉하지 않는다** (game-design §6). 애니메이션 중 들어온 입력은 버린다.

## 완료 기준

- [x] 모바일 에뮬레이터에서 스와이프 4방향이 동작한다 — **위젯 테스트의 `tester.drag` 로 검증.** 실기기 확인은 못 했다
- [x] `-d chrome`에서 페이지 로드 직후 클릭 없이 방향키가 먹는다 — `autofocus` + "진입 직후 방향키" 테스트
- [x] 데스크탑 빌드에서 방향키·WASD·**R**이 동작한다 — **`Z`(되돌리기)는 제외.** undo 스택이 `07` 의 몫이라 지금은 연결할 대상이 없다
- [x] ~~화면 방향 버튼이 세 플랫폼 모두에서 동작한다~~ — **이후 제거됐다** (아래 정정 절)
- [x] 애니메이션 중 연타해도 보드가 꼬이지 않는다 — `state.canMove` 게이트. 연출은 `06` 에서 붙지만 게이트는 이미 `isAnimating` 을 본다
- [x] 스와이프 방향 판정 로직에 단위 테스트가 있다 — `directionFromSwipe` 순수 함수 + 12건

## 열린 질문

- 마우스 드래그를 스와이프로 취급할지
  → **취급한다.** `GestureDetector` 의 기본 동작을 그대로 뒀다. 끄려면 별도 코드가 필요한데, 웹에서 드래그가 먹는 편이 자연스럽고 방향 버튼과 중복돼도 해가 없다
- 게임패드 지원 — v1 제외
- 방향 버튼을 항상 보일지, 터치 기기에서는 숨길지
  → **제거로 해소.** 아래 정정 절 참고

## 실제 결과


**결정 사항**

- **`KeyboardListener` 가 아니라 `Focus` 를 쓰고, 처리한 키는 `KeyEventResult.handled` 로 소비한다.** 처음에 `KeyboardListener` 로 짰더니 방향키가 그대로 위로 흘러 Flutter 기본 포커스 이동(`DirectionalFocusIntent`)까지 타서, 한 번 누르면 포커스가 AppBar 버튼으로 떠나고 그 뒤로는 방향키가 먹지 않았다. **테스트가 이걸 잡았다** — `↑ ↓ ← →` 를 연달아 눌렀을 때 `↓` 가 유실됐다.
- **`KeyDownEvent` 가 아닌 이벤트도 매핑된 키라면 삼킨다.** 반복·뗌 이벤트를 흘려보내면 그것들이 포커스 이동을 일으켜 같은 문제가 난다. 동작은 여전히 누름 1회당 1수다.
- **화면 버튼을 누른 뒤 포커스를 되돌린다.** 버튼이 포커스를 가져가면 방향키가 죽는다. 버튼을 `canRequestFocus: false` 로 막는 방법도 있지만 그러면 Tab 접근성이 사라진다. 버튼은 그대로 두고 조작 후 `requestFocus()` 하는 쪽을 골랐다.
- **결과 오버레이가 닫힐 때도 포커스를 되찾는다** (`didUpdateWidget`). 오버레이의 "다시하기" 를 누르면 그 버튼이 포커스를 가진 채 오버레이가 사라지기 때문이다.
- **임계값은 우세한 성분에 적용한다.** 대각선으로 합친 거리가 임계값을 넘더라도 가로·세로 성분이 모두 미달이면 무시한다 — 어느 방향을 의도했는지 알 수 없는 입력을 넘겨짚지 않는다. 두 성분이 정확히 같으면 가로가 이긴다(임의의 선택이지만 테스트로 고정).
- **스와이프 누적은 `onPanUpdate` 에서 한다.** `onPanEnd` 는 속도만 주고 총 이동량을 주지 않는다.
- **입력 게이트는 `state.canMove` 를 재사용한다.** task 문서의 예시는 세 플래그를 다시 나열하지만, `04` 에서 만든 게터가 이미 같은 판정을 한다. 두 곳에 같은 조건을 적어두면 언젠가 갈린다. Notifier 쪽 게이트가 최종 권한이고 화면 쪽은 불필요한 이벤트를 줄이는 역할이다.

## 남은 사항

- **`Z` / `Ctrl+Z`(되돌리기)는 연결하지 않았다.** undo 스택이 없어 붙일 대상이 없다. `07-undo-reset` 에서 `_directionForKey` 옆에 한 줄 추가하면 된다.
- **실기기·실브라우저 확인을 못 했다.** 세 입력 경로 모두 위젯 테스트로 검증했지만, 실제 터치 제스처의 손맛(임계값 24가 적절한지)은 사람이 만져봐야 한다.

## 정정 (2026-08-05) — 화면 방향 버튼 제거

**이 문서의 작업 §3(화면 방향 버튼)과 완료 기준의 해당 항목은 더 이상 유효하지 않다.** 사용자 요청으로 D-pad 를 없앴다. 화면에 남는 조작은 **다시하기 하나**다.

당시 이 문서는 "마우스만 쓰는 사용자와 접근성 때문에 항상 제공한다" 고 적었는데, 실제로는 세 플랫폼 모두 대체 경로가 있다.

| 플랫폼 | 남은 입력 |
|---|---|
| 모바일 · 터치 | 스와이프 |
| 웹 · 데스크탑 | 방향키 · WASD · **마우스 드래그** |

마우스 드래그를 스와이프로 취급하기로 한 결정(이 문서의 열린 질문 1)이 여기서 값을 했다. 그게 없었다면 마우스 전용 사용자가 조작할 방법이 사라졌을 것이다.

**발견성 문제는 튜토리얼로 풀었다** (기획서 §6.1). 레벨마다 안내 문구를 붙일 수 있고, 그 레벨에 **처음 도달했을 때 오버레이로 한 번** 뜬다. 조작 안내는 레벨 1에서만 추가로 붙으며 플랫폼에 따라 문구가 다르다(터치 → 스와이프 / 그 외 → 방향키 · WASD).

> 처음에는 보드 아래 한 줄로 뒀다가 걷어냈다. **사라질 때 보드가 갑자기 커져 시선이 흔들렸기 때문이다.** 오버레이는 판 위에 겹치므로 나타나고 사라져도 레이아웃이 움직이지 않는다.

열린 질문 3("방향 버튼을 항상 보일지, 터치 기기에서는 숨길지")은 **제거로 해소**됐다. `10-responsive` 로 이월할 필요가 없다.
